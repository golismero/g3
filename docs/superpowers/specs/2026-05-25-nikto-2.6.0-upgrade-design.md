# Nikto Plugin Upgrade to 2.6.0 — Design Spec

**Date:** 2026-05-25 (rev. 2026-05-26: rebased on Magenta's parser; rev. 2026-05-29: implementation outcome)
**Status:** Implemented — Tiers 1–3 shipped and user-verified (2026-05-27 to 2026-05-29); Tier 4 deferred.
**Plugin:** `plugins/attack/nikto/`

## Problem

The Nikto plugin installs Nikto via `apk add nikto`, pinning to whatever version Alpine
ships — non-reproducible, and the output format drifts under us. The importer (`g3i.py`)
was written against a very old Nikto (1.x-era, port-less CSV) and misparses or breaks on
modern output. Three concrete problems:

1. **No version pin.** `apk add nikto` is non-reproducible.
2. **Schema drift in 2.6.0.** Modern Nikto (2.5.0+) removed OSVDB as the primary
   identifier, replacing it with a free-text `references` field. The importer's OSVDB-based
   data model no longer matches.
3. **Single fragile format.** Only CSV is parsed, against an obsolete column layout.

## Decision: rebase on Magenta's Nikto parser

A sibling tool, **Magenta** (the g3 reporting companion, `../magenta`), independently solved
this exact problem — see `private/magenta/parsers/nikto/nikto.py` and its design at
`private/magenta/docs/superpowers/specs/2026-05-25-nikto-parser-update-design.md`. We adopt
its architecture and port its parser into a g3 importer, rather than designing our own.

**What we take from Magenta (port, adapting only the output shape to G3Data):**
- The **normalize-then-emit** architecture: per-format readers → neutral `Finding` →
  `classify_references` → `build_issues`.
- `classify_references` / `_classify_token`: whitespace+comma tokenization, scheme routing
  (CVE/MS/CNVD/OSVDB → per-finding `cve`; CWE/CAPEC/RFC/KB → taxonomy; URLs → references;
  BID drop), token-keyed overrides (Phorum `CVE-2002-0764`), concept hardcodes
  (`CA-2000-02` → `CWE-79`), known-junk drops (`WS_FTP.LOG`), loud-warn on unknown tokens.
- The **OSVDB colon-key fix** (`osvdb2cve["OSVDB:<n>"]`) and the **OSVDB hit-rate guard**
  (loud warning when many OSVDB ids resolve to zero CVEs — catches key-format drift).
- The populated, Wayback-sourced **`osvdb2cve.json`** (colon-keyed, with the Phorum
  `OSVDB:11144/11145 → CVE-2002-0764` entries). Validates the map our generator produces.
- Hardened, tolerant `read_xml` (XXE/billion-laughs guards; doubled-`niktoscan` and
  not-well-formed tolerance; recursive `<item>`; refs from `<references>` child *or*
  `osvdblink` attr); `read_json` (2.6.0 array + 2.5.0 fragment repair); `read_csv`
  (skip SSL-info `000137` rows, strip CSV-injection `'`, skip host-start rows).

**Architecture change vs the original draft:** we drop the planned hybrid precompute
(`gen_taxonomy.py` + `nikto_taxonomy.json` keyed by `nikto_id`) and the JSON-first wrapper
migration. Magenta proves a **pure runtime token classifier** is sufficient and
**format-agnostic** — it keys special cases on the reference *token* (unique per test), not
`nikto_id`, precisely because CSV carries no id. This is simpler and handles synthetic-ID
findings too. The live wrapper stays on CSV (unchanged).

## Our three improvements over Magenta (contribute back)

Verified gaps in Magenta's current parser that g3's data demands:

1. **Unicode-hyphen CVEs.** Magenta's `_CVE_RE` is ASCII-only and it normalizes no hyphens,
   so the ~20 `CVE‑2002‑1929` (U+2011) tokens in `db_tests` fall to its
   "unrecognized → loud-warn + drop" path, silently losing real CVEs. **Fix:** normalize
   U+2011 (and other Unicode hyphens) → ASCII `-` before matching.
2. **2.1.5's real buggy 6-field CSV.** Magenta's `read_csv` does `if len(row) < 7: continue`,
   skipping the 6-field item rows produced by 2.1.5's port-merge bug (exactly what
   `samples/nikto.csv` contains). **Fix:** discriminate by per-item-row field count —
   6-field (2.1.5 bug: `OSVDB` at col 2) vs 7-field (post-fix/2.5.0+: refs/OSVDB at col 3).
3. **Taxonomy-derived URL collapse.** Magenta routes *all* `http(s)://` tokens to
   references, so `vulners.com/osvdb/OSVDB:2889` and the `999993` ssl finding's
   `cwe.mitre.org/.../297.html` become reference links instead of `OSVDB-2889`/`CWE-297`
   taxonomy. **Fix:** collapse taxonomy-derived URLs to their ID (user requirement: don't
   duplicate a linkified taxonomy id as a reference); genuine non-taxonomy URLs still go to
   references.

## Goals

- Pin Nikto to a known-good **2.6.0** source build (reproducible, overridable).
- Port Magenta's parser into `g3i.py`, emitting the existing **G3Data** issue contract.
- Correctly parse CSV (live), then JSON and XML (external/legacy ingestion), across all
  obtainable Nikto versions (2.1.5 → 2.6.0).
- Apply the three improvements above.

## Non-Goals

- **OSVDB→CVE map generation.** `misc/osvdb2cve.py` and its build wiring are fixed and out
  of scope; the importer just consumes the working map.
- **Per-finding severity / CVSS.** Findings stay `severity: 2` (high), as today.
- **JSON-first wrapper migration.** The live wrapper stays CSV. JSON output is a possible
  future enhancement, not part of this work.
- **1.x (truly port-less) CSV support.** Unobtainable; never existed in Nikto's git history.
- **Template/category routing** (Magenta's deferred "Phase B"). g3 maps issues via plugin
  i18n, not magenta templates; not in scope.
- **Tag-less / non-CVE Nikto findings.** Nikto's check-plugin findings that carry no
  taxonomy tag (e.g. missing security headers, BREACH, directory indexing, the Cloudflare
  proxy note) are **dropped by default** (only `INCLUDE_INFO` surfaces them). g3's goal here
  is surfacing *known vulnerabilities* (CVE/CWE/OSVDB/etc.), matching Magenta. Confirmed
  decision: this means a scan of a target with only header-hygiene issues yields an empty
  Nikto report — that is correct, not a bug.
  - **Deferred future work (later version):** if we later surface these extra findings,
    they must be emitted as **tool-agnostic G3Data** so the merge step deduplicates them
    across tools — e.g. a Nikto-detected BREACH should use the *same* issue shape testssl
    would emit, so a scan running both tools doesn't double-report it. Doing this properly
    is non-trivial (it's why Magenta deferred it to Phase B); defer unless explicitly
    prioritized.

## Key findings (retained from research)

### OSVDB gone as primary; `nikto_id` + free-text `refs` replace it (2.5.0+)

- 2.6.0 findings carry a 6-digit `nikto_id` (internal test-DB index, **not** a public
  taxonomy) and a free-text `refs` field conflating taxonomy IDs and URLs.
- `refs` mixes CVE / CWE / **OSVDB (38 still present in 2.6.0)** / MS bulletins / CERT-CA /
  CNVD / RFC tokens and raw URLs, delimited by **whitespace and commas**.
- Data-quality traps: comma-joined tokens, **Unicode-hyphen CVEs** (U+2011),
  taxonomy-derived URLs (`vulners.com/osvdb/OSVDB:2889`, `cwe.mitre.org/.../297.html`),
  and corruption (`OSVCVE-2011-339244`, the Phorum mis-tag `CVE-2011-3392`).

### Findings come from DB + check plugins; the discriminator is the tag, not the engine

- Bulk findings come from `db_tests`; ~41% carry **no reference** and are informational
  recon observations. Check plugins (`nikto_headers`/`cookies`/`ssl`/…) emit mostly
  untagged hygiene findings, but carry a CVE when they identify a specific software vuln
  (e.g. `999984`→`CVE-2003-1418`, `999991`→`CVE-2006-4352` conditionally,
  `999993`→`cwe.mitre.org/.../297.html`).
- **Inclusion rule:** report a finding iff it resolves to ≥1 taxonomy tag; untagged →
  informational, dropped unless `INCLUDE_INFO`. This matches the old parser's `OSVDB-0`
  behavior and is reference-token-based, so it needs **no `nikto_id` and no plugin-source
  pre-parsing**.

### Output format facts

- **CSV does not emit `nikto_id`** (only `refs`) — which is why token-keyed classification
  (not id-keyed) is the right design.
- 2.1.5's **host line** parses to 7 clean fields; its **item lines parse to 6** due to a
  runtime `SCALAR`/quoting bug that merges `ip+port`. The current importer's column indices
  are correct for *this buggy 2.1.5 output*, not a 1.x format.
- XML root changed `niktoscan` → `niktoscans` (2.5.0); `nxmlversion` stayed `"1.2"`
  (useless for version detection); items dropped `osvdblink`, gained `<references>`.
- JSON added 2.5.0 (sometimes invalid for multi-host), rewritten to a valid array in 2.6.0.

### Latent g3 bug to fix during the port

- The current `g3i.py` XML path sets `issue["_start"] = <datetime>`, which `json.dump`
  cannot serialize — a crash dormant only because the live wrapper emits CSV. Magenta hit
  and removed the same bug. **Drop `_start`/`_end` datetime objects** (or serialize to
  strings) in the port.

## Architecture: normalize-then-emit (single file, G3Data output)

```
main()                    detect format → dispatch → json.dump(build_issues(findings))
  ├─ read_xml(text)  ─┐
  ├─ read_json(text) ─┼─►  list[Finding]            Finding = {host_url, path, method,
  └─ read_csv(text)  ─┘                                        refs_str, nikto_id, msg}
classify_references(refs_str, nikto_id) ─► {cve, taxonomy, references}   # written ONCE
build_issues(findings)                  ─► [G3 issue obj]               # written ONCE
```

`classify_references` is ported from Magenta plus the three fixes (Unicode-hyphen
normalization; URL→taxonomy collapse). `build_issues` is adapted to emit the **G3Data**
issue object, not the magenta contract:

```
{ "severity": 2, "affects": [sorted host+path urls],
  "taxonomy": [sorted union of cve+taxonomy tags], "references": [sorted URL refs],
  "issues": { host_url: [ {path, cve, msg}, … ] },
  "_cmd": <nikto cmdline>, "_fp": [<"nikto scheme://host/">], "_artifacts": ["nikto.csv"] }
```

(`_fp`/`_cmd`/`_artifacts` preserved from the current importer; `taxonomy`/`references`
dropped when empty; `returns: "issue"`.) `read_csv` adds the 6-vs-7-field discriminator.

## Tier breakdown

Status as of 2026-05-29. Per-tier execution detail lives in
`docs/superpowers/plans/2026-05-26-nikto-2.6.0-upgrade.md`.

### Tier 1 — Pin to 2.6.0 from source — SHIPPED

- `Dockerfile`: replace `apk add nikto` with a source build mirroring the testssl pattern —
  `git clone --depth 1 --branch ${BUILD_VERSION}` from `github.com/sullo/nikto`, overridable
  `ARG BUILD_VERSION=2.6.0`.
- Keep the current CSV wrapper and existing importer working as-is in this tier.
- Pure infrastructure; independently shippable and verifiable.

**Follow-up (emerged during verification, against the *tagged* source):**

1. Nikto 2.6.0 treats `-o` as a *base name* and unconditionally appends `.<format>` (the
   "append only if not already present" guard exists only at HEAD, not at the tag), so
   `g3p.sh` was changed to `-o /artifacts/nikto`.
2. The previous wrapper's `cat … | g3i` pipeline + unconditional `exit 0` swallowed
   failures as silent `DONE`; `g3p.sh` now uses `set -o pipefail`, captures Nikto's `rc`,
   and ends with `exit $rc` — matching the nmap/wafw00f/subfinder sibling convention.
3. Console output is now `tee`'d to `/artifacts/nikto.txt` (parity with sibling plugins).

Sibling additions: `nikto.g3p` invariants hoisted into the wrapper; `nikto-slow.g3p`
added as a paced variant (selectable as `nikto-slow`, nmap-variant pattern).

### Tier 2 — Core importer rewrite (CSV path live) — SHIPPED

- Ported `Finding` / `classify_references` / `_classify_token` / `read_csv` etc. from
  Magenta (bringing the three g3-originated fixes along).
- New `build_issues` emits **G3Data** (`severity: 2`, `_cmd`, `_fp` per-host with
  default-port stripping, `_artifacts: ["nikto.txt", "nikto.csv"]`, no Magenta `tools`/
  `template`).
- OSVDB colon-key resolution + hit-rate guard; reuse the populated `osvdb2cve.json`
  (loaded CWD-relative for g3's container layout, not `__file__`-relative).
- Tag-less findings dropped by default (`INCLUDE_INFO` flag preserved).
- Latent `_start = datetime` → `json.dump` crash removed.
- Live wrapper unchanged (CSV). Plugin fully functional after this tier.

### Tier 3 — JSON reader (external/legacy ingestion) — SHIPPED

- Ported `read_json`: 2.6.0 array of host objects + 2.5.0 concatenated-fragment repair
  (`}{` → `},{` then wrap); loud warning + `[]` on unrepairable input.
- Wired into the `main()` format sniffer. XML branch still defers (Tier 4).

### Tier 4 — XML reader (external/legacy ingestion) — DEFERRED

Scope unchanged; preserved for a future pickup.

- Port `read_xml`: hardened lxml parser (XXE/billion-laughs), tolerant of doubled
  `niktoscan` and not-well-formed XML, recursive `<item>`, refs from `<references>` child or
  `osvdblink` attr; handle `niktoscan`/`niktoscans`; multi-host.

**Deferred** because the live wrapper emits CSV (Tier 2 covers it) and JSON is covered
by Tier 3; external-XML ingestion isn't a current need. The `Finding` seam means the
classifier and `build_issues` will pick the XML reader up unchanged when added.

## Risks / open questions — outcomes

- **G3Data adaptation of `build_issues`** — *resolved:* `_fp` per-host with default-port
  stripping (new `_fp_host` helper), `_artifacts: ["nikto.txt", "nikto.csv"]`, `_cmd` from
  `sys.argv` when called from the wrapper.
- **`osvdb2cve.json` to ship** — *resolved:* g3's own generator (`misc/osvdb2cve.py`,
  Wayback-sourced after the original URL went dead) produces a colon-keyed map; same shape
  as Magenta's. Importer loads it CWD-relative for g3's layout.
- **URL→taxonomy collapse** — *implemented* for MITRE CWE / CAPEC, vulners OSVDB, and
  NVD/MITRE CVE; unknown taxonomy-host URLs fall back to references.
- **Convention conflict (Magenta TDD vs g3 user-owned tests)** — *honored:* porting kept
  g3's conventions (no agent tests, lint + build verification, user-owned git). Magenta's
  test suite was kept green there separately (`tests/test_nikto_parser.py`, 60 passing).
